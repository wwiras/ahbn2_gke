## Authoritative metric definitions

The single-run authoritative implementation is `app/plot_exp10.py:34-47`; `scripts/run_experiment.sh:117-122` invokes it and supplies the configured node count.

### delivery_ratio

```text
delivered_peers = number of distinct peer_id values in received_new
delivery_ratio = delivered_peers / expected_nodes
```

The source peer is included because StartRun calls `process_envelope` locally and emits `received_new` for peer 0. In this run the explicit denominator is all 8 configured nodes. No inactive-peer exclusion is implemented.

### propagation_delay

```text
max(ts of received_new) - min(ts of message_injected), in seconds
```

This is source creation/injection to final unique reception (completion delay), not first-delivery or mean delay.

### duplicates

```text
number of received_duplicate records
```

`app/peer.py:575-616` checks `seen_messages`, increments the duplicate counter, emits `received_duplicate`, and returns before target selection. A duplicate cannot emit `received_new` or refanout.

### total_forwards

```text
number of forward records
```

`app/peer.py:509-535` emits `forward` only after a gRPC response with `resp.ok`. Thus this counts successful sends, not attempts. `forward_rejected`, `forward_failed`, controller, churn, and maintenance events are excluded.

## Raw event schema and timestamp semantics

Actual dissemination fields are `event`, `ts`, `message_id`, `peer_id`, `src_peer`, `dst_peer`, `hop`, `strategy`, `mode`, and `latency_ms` where applicable. There is no duplicate boolean; duplicate classification is the event type. Controller traces have controller observation fields and no message ID.

`ts` is a floating-point Unix epoch value in seconds produced by `time.time()` (`app/utils.py`). `message_injected` records source creation/injection. `received_new.ts` is the receiving process's wall clock. `forward.ts` is logged by the sender after the receiving RPC returns successfully, so it is a successful-send-completion timestamp and normally follows the corresponding receive timestamp. End-to-end `latency_ms` is computed from the creation timestamp carried in the envelope. No negative latency occurred.
