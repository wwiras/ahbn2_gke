## O. Implemented availability and maintenance model

`app/dcsoc_maintenance.py` owns one per-peer replica of the canonical
DC-SoC active map and structural state. Its locked transition method implements
ACTIVE→INACTIVE and INACTIVE→ACTIVE exactly once; repeated evidence is a
no-op. Every real transition records measured wall/performance-clock start,
end, duration, reason, action, and relevant node/cluster provenance.

`app/controller.py` broadcasts DC-SoC maintenance only when the topology's
strategy is `dcsoc`. Fail-stop and pod deletion broadcast leave; pod recovery
replays the missed leave to the recreated pod and then broadcasts rejoin.
Gossip, Structured, and AHBN return before this RPC path. Overload never calls
it.

## P. TAIL and CORE local repair

A TAIL leave removes only its active parent edge and parent child-reference.
It does not elect a CORE or recluster. A CORE leave removes affected edges and
elects among active members of that same retained cluster using original
physical degree, then lowest ID. The failed/inactive node is excluded. If no
candidate exists, no replacement is recorded and the affected branch remains
detached without importing a foreign node.

When a replacement exists, only the affected parent/children and downstream
CORE-chain reference are transferred. Unrelated cluster members and branches
remain unchanged. Static forwarding still consumes the same K3.4
`dcsoc_parent`/`dcsoc_children` fields, so repaired forwarding remains
unbudgeted and preserves sender/self exclusion and duplicate suppression.

## Q. Rejoin scope

A returning peer is restored exactly once to its previous cluster when that
cluster still has an active CORE. A former CORE returns as a leaf and does not
displace its replacement. The invalid-previous-cluster/new-peer case is not
required by the current frozen Exp11 orchestration, and ControlSim supplies no
general nearest-cluster lifecycle rule; arbitrary reassignment/scale-out was
therefore not invented. Explicit `du` is the canonical way to reconsider all
currently active peers.

## R. Explicit `dcsoc_recluster` / `du`

`ApplyDCSOCMaintenance` exposes an explicit `du` request. It atomically selects
active peers, builds their current physical induced graph, and directly calls
the frozen K3.4 `assign_dcsoc_clusters` implementation with the retained
`eps`/`min_samples`. It refreshes roles/edges and increments `recluster_count`
and `structural_generation`. There is no timer, inferred cadence, sleep, or
synthetic repair penalty. Repeating `du` on unchanged state deterministically
reproduces the same structure.

## S. Instrumentation

Each completed action records `maintenance_start`, `maintenance_end`, measured
nonnegative `maintenance_duration`, `maintenance_reason`, and action-specific
provenance. State counters are `core_replacement_count`, `recluster_count`, and
`rejoin_assignment_count`. Instrumentation is written only after decisions and
does not influence election, clustering, or forwarding.
